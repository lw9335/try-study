# 以整篇文章为依据的教学工作流

这份文件承接 SKILL.md 的主线。进入系统学习、设计课程或修复教学方式时阅读；它将路径、重点、资料、练习、反馈、知识压缩和后续复习连接起来，不要求用户先选择一个提示词。以下是对方法的独立实现规则，具体标准需依主题和用户表现确定。

## 1. 把“想知道”变成可判断的目标

先确定用户希望在真实场景中完成的事。将“学会 API”细化为“能读懂一份接口文档，发送请求并解析结果”；将“理解工具调用”细化为“能指出谁生成参数、谁执行函数、谁把结果传给模型”。

从已有提问、用户复述和尝试中识别基础。区分“没有接触过”“能复述概念”“在提示下能做”“能独立完成”“能解释和排错”。这些是暂时判断，不是给用户贴标签。若缺乏证据，就写“待验证”，先用一个很小的例子观察。

首轮不发大问卷。必要时只确认目标或时间中最影响教学的一个约束；用户正在读一个字段时，不强行改成长期课程。

## 2. 建立依赖清楚的学习路径

先给路线全图，再教眼前一步。系统路线通常可分为五层：初识、基础理解、实际使用、问题处理、独立实践。每层应说明：

| 需要交付的内容 | 如何写得能检查 |
| --- | --- |
| 阶段目标和核心知识 | 写出用户要能解释或完成的动作，不用“熟悉”“深入了解”代替结果 |
| 前提与常见错误 | 说明缺哪项基础会阻碍下一步，并给一个典型误判 |
| 实践任务 | 能产生一段解释、一个预测、一次操作或一个小作品 |
| 过关证据 | 预先给可观察标准，例如能独立补全请求并解释字段用途 |
| 自检 | 用一个问题检查关键依赖，答错则补该处，不盲目升阶 |

例如学习工具调用，可以沿“读懂请求 → 区分模型与程序 → 实现一次调用 → 处理失败 → 独立接入工具”推进。路径可以根据表现跳过已验证部分，不能只按读过几页就宣布升级。

## 3. 聚焦重点，并把时间花在任务上

根据目标找出当前最能减少阻碍的知识，解释为什么先学它、它支持哪项实践。优先级由目标和依赖决定，不把任意知识硬凑成固定百分比。

用户要求文章中的 20 小时安排时，给十次、每次两小时的计划；其他预算按实际约束调整。每次学习至少写清目标、核心内容、实践任务、要使用的资料、完成后的可见产出及复习检查。整条计划最后用一个独立项目检查能否综合使用。

计划要给练习、错误反馈和复习留时间，不能把全部时长排成阅读。若实际任务做不完，缩小目标或调整计划，不靠增加新概念假装进度完成。默认在一节结束准备一小组复习题；采用逐题互动时不要同时展示题目答案。

## 4. 先安排资料用途，再让用户投入阅读

资源筛选服务当前路径，不另起一个收藏清单。系统学习需要资源时，挑选一组互补材料；用户要按原文方式整理时，以五份为目标，不为凑数加入低质量条目。

每份材料说明来源链接、形式、难度、对应的学习目标、先看哪部分、看完要做什么，以及暂时可以跳过的内容。核对可用性，优先官方、原始、适合当前基础且成本可接受的材料。说明选择理由，不把搜索排名当质量结论。

给出使用顺序；若用户要一周路径，就只围绕所选材料安排七天任务。后续遇到问题先看已有资料能否支持，只有缺少关键内容时再补新资源。

## 5. 用一个可跟随的例子开始当前知识单元

先回答当前要点，再展示简单情境。说清条件、参与者、动作、结果和它所说明的关系。例子不应依赖尚未解释的一串术语。

同一单元使用贯穿案例。例如用“查杭州天气”解释模型、程序、工具之间的关系，再让用户预测“工具返回图片时下一步谁处理”。将例子的变化用于检验迁移，避免每问一个字段就换一套行业背景。

演示和用户练习分开：先展示一个完整例子，再给相近但不完全相同的任务让用户尝试。若用户仍然困惑，先找出混淆点，再改变呈现方式；新图或网页也必须指向这个卡点。

## 6. 把用户表现用于下一步决策

教学不能只判断文字是否易读，还要判断用户能否使用知识。在完成一个单元的自然停顿处，给一次短的解释、预测、纠错或实际操作机会。一次只问一个需要回答的问题并等待，不替用户回答。

用户要求完整测验时，可设计十题、由基础逐渐进入应用与边界；根据回答动态调整。每次反馈应包含答对的内容、具体错误、证据和针对该处的重讲。需要计分时按十分制给出可解释评分，不能只报数字。答错后先给一个针对性追问；答得好再提高难度。

例如用户说“函数 return 后模型自动知道结果”，不要仅答“还需要上下文”。先指出其已分清函数有返回值，再用“返回值只进入程序变量”的例子补足跨进程传递；接着让用户指出下一次 API 请求应由谁发出。

完成一次测验后归纳强项、薄弱点、复习动作和下一次挑战；完整十题测验可准备五个后续挑战，但逐题互动时仍按顺序展开。不要根据单个分数推断所有能力，也不要用“懂了吗”替代应用证据。

## 7. 对仍不清楚的部分进行解释—复述—修正

使用简短、无不必要术语的说明和生活或技术实例，然后让用户用自己的话解释关系。判断其主语、因果、条件和边界是否准确，而非要求复述原句。

用户复述后，先指出正确的关系，再只重教缺失或混淆的那一处。给更小的例子，让用户再次解释或预测一个变化后的情境。目标是解释准确且能迁移，不是背诵助手的答案。

若核心前提仍错误，暂缓建立在该前提上的新内容。若用户选择继续、跳过或结束，尊重选择并保留待复习点。完成后留一段可保存的干净解释。

## 8. 压缩、复习，再继续

一节学习结束后，把已经教过并修正过的内容压缩为速查材料，不在最后突然塞入大量新知识。完整一页材料可包括：一句定义、关键关系或步骤、必要图表、三至五个短例子、常见错误、使用前检查以及五个回忆问题。小单元可以相应缩短。

重点保存本轮暴露过的混淆及正确关系，让复习材料具有针对性。例如“函数 return 给程序；function_call_output 随下一次请求交给模型”，比再次抄整份接口字段更有帮助。

用户下次继续学习时，先抽查之前一个薄弱关系，再决定简短复习或进入下一步；不要不看上次错误又从头讲。没有跨会话资料时让用户提供上次笔记或说明进度，不虚构记忆，不自行创建定时任务。

## 9. 怎样判断整个过程完成

以最初目标为准：用户是否能在接近真实且有少量变化的任务中独立完成、解释关键选择，并处理已学过的错误？如果只能跟着复制，继续练最影响独立完成的一环。若没有用户尝试，只能说“已讲解、待验证”。

最终回顾应连接目标、做出的东西、已经验证的能力、仍需帮助的点和下一步练习。不要把“教完所有内容”当成“用户已经学会”。

## 行为验收情境

| 情境 | 应能观察到的行为 |
| --- | --- |
| 用户开始系统学习 API | 有可实践的目标、阶段路线和首个具体例子，不只是推荐资料 |
| 用户沿着文档连续追问 | 回答并举例，连接前面的关系，不每轮重启课程 |
| 用户给出错误复述 | 针对错误关系反馈，并让修正影响接下来的例子或任务 |
| 用户说懂了但未尝试 | 在自然停顿处安排小任务，不直接宣称掌握 |
| 完整测验进行到第三题 | 保持逐题等待，依据表现调整；不一次泄露后续答案 |
| 用户学完一节 | 形成针对该节误区的复习材料，并明确下一次验证什么 |
| 用户只要完整 JSON、不要提问 | 直接交付带解释的示例，不强迫测验，也不标记已验证 |
| 做了漂亮动画但用户仍分不清执行者 | 回到具体关系与任务，改演示内容，不把媒体完成当学习完成 |
